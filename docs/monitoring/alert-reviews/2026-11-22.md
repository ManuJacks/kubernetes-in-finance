## Finding 1: false page after the host woke from suspend

**What happened.** The desktop host resumed from suspend at 04:21:06 UTC
(23:21 EST; host journal: `System returned from sleep operation
'suspend'`). As the VMs resumed, one probe failed at 04:21:10 UTC, both
through the VIP and directly to `tf-ha-control2`; all later probes passed.
`ApiAvailabilityFastBurn` fired 04:24 to 04:26 and `ApiAvailabilitySlowBurn`
04:37 to 04:49. Alertmanager delivered about three notifications to ntfy,
with no failures.

**Why it paged.** The burn-rate windows held almost no samples: Prometheus
had been suspended too. One failure among the few samples taken since
resume looked like an error rate of several percent, far above the 1.44%
fast-burn threshold. The rule measured the monitoring gap, not the platform.

**Actionable?** No. The platform was healthy; there was nothing to do.

**Records.** [PRB-2026-11-22](../../problems/PRB-2026-11-22-false-page-after-host-suspend.md) (no INC: the platform was healthy) and [CHG-2026-11-22](../../changes/CHG-2026-11-22-burn-rate-data-guard.md).

**Change (this PR).** Burn-rate pages now require each long window to hold
at least half its expected samples (`count_over_time >= 180` for 1 h,
`>= 1080` for 6 h). A real outage still produces failed probes and so still
pages; MTTD tests are unchanged. A `promtool` regression test replays this
exact sequence (an hour of data, a 2-hour gap, one failure, recovery) and
asserts no page. Trade-off, recorded in ADR-006: after a monitoring gap,
fast-burn paging resumes once 30 minutes of data exist.

**Open: the host still suspends.** This is the second incident caused by
host suspend (see the
[clock drift incident](../../incidents/2026-11-21-clock-drift-after-host-suspend.md)).
The platform, its monitoring and the backup store all run on this desktop.
Owner decision needed:

- *Disable suspend while the lab is running* (`sudo systemctl mask
  sleep.target suspend.target hibernate.target hybrid-sleep.target`).
  Removes the cause. Uses more power.
- *Accept suspend as a planned outage.* Keep the data guard, and add an
  Alertmanager silence or inhibit tied to host resume.

Recommendation: disable suspend. A platform that claims a 99.9% SLO cannot
be paused overnight. The SLO window currently counts suspended time as
neither good nor bad, which flatters the number.

## Finding 2: abandoned workloads

Neither is in the repository; both were applied by hand.

**`default/readiness-demo`** (created 2026-11-10). A Deployment whose
readiness probe requests `/missing` on nginx, so it is never Ready by
design. It has failed its probe about 26,000 times in the last 38 hours.
The alert is a correct true positive.

**`debug-system/production-debug`** (12 days old). The bare debug pod used
in the 2026-11-21 game day. It is in phase `Failed` (restart policy
`Never`), on `tf-ha-control3`. Its spec deserves attention regardless:
memory limit 2 GiB (larger than a worker, about the size of a control-plane
node), `NET_ADMIN`, `NET_RAW` and `SYS_PTRACE` capabilities, and a
control-plane toleration. No alert fired: no rule covers a Failed bare pod.
That gap is accepted; bare pods are not managed workloads, and the
dashboard's "Unhealthy pods" table shows it.

**Recommendation.** Delete both (the live specs are in their
`last-applied-configuration` annotations if needed again). Keep demo
workloads in the repository (`kubernetes/`) with an owner and a removal
date, so the next review can tell intended failures from neglected ones.

```bash
kubectl -n default delete deployment readiness-demo
kubectl -n debug-system delete pod production-debug
```
